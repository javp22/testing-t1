# Agente de generación automática de tests

## Estrategia y arquitectura

El agente recibe un archivo Python y crea una suite `pytest` en cuatro fases. Primero, `build_generation_prompt` entrega el código fuente al LLM y exige imports válidos, casos normales, límites y excepciones. Luego ejecuta `pytest`; si falla, `build_fix_prompt` devuelve el código, la suite y el log para que el LLM corrija el error. Cuando la suite pasa, mide cobertura de líneas y ramas con `coverage`. Si no alcanza 80% y 50%, respectivamente, `build_coverage_prompt` entrega las líneas y ramas faltantes para generar otra versión. Finalmente ejecuta Cosmic Ray y calcula el mutation score a partir de `cr-rate`; los mutantes sobrevivientes se entregan a `build_mutation_prompt` para reforzar aserciones específicas. Cada candidato que rompe `pytest` se descarta y se conserva la última versión estable. El proceso tiene un presupuesto de 105 segundos y reintentos limitados para la API.

Los prompts comparten reglas que restringen al modelo al código entregado, prohíben aserciones triviales y piden devolver solamente Python ejecutable. La separación por objetivo funciona bien: cobertura encuentra caminos no ejecutados y mutación verifica si las aserciones distinguen el comportamiento correcto del mutado. Una mejora sería registrar cada prompt, respuesta, duración, fallo e iteración; además, convendría ejecutar primero una validación estática y usar un presupuesto adaptativo por archivo.

## Desafíos técnicos y limitaciones

La mayor complicación práctica fue integrar Cosmic Ray: requiere generar una configuración temporal con rutas relativas, crear una base SQLite, ejecutar los mutantes dentro de límites de tiempo y traducir la tasa de supervivencia a mutation score. También aparecen dependencias ausentes o imports frágiles en los proyectos evaluados. Para hacer ejecutables algunos tests el LLM sustituyó módulos con `MagicMock` o modificó `sys.modules`, aunque la regla del prompt pedía no reemplazar la lógica bajo prueba. Finalmente, una API gratuita o de baja prioridad puede estar saturada: los reintentos y la latencia consumen el presupuesto y pueden dejar una ejecución incompleta.

## Calidad de los tests

Se generaron 20 suites, con 174 funciones de test y 387 verificaciones explícitas. En 14/20 objetivos se alcanzaron simultáneamente los umbrales de cobertura; 12/20 alcanzaron mutation score >= 50%. Entre las 12 sesiones con mutation score no nulo, los promedios fueron 98.7% de líneas, 87.9% de ramas y 83.3% de mutación. Hay seis resultados con todas las métricas en cero y dos casos adicionales con cobertura alta pero mutation score cero (`mahjong/dealer` y `stock4/validate`), evidencia de que cubrir líneas no prueba por sí solo la calidad semántica.

Hay aserciones pertinentes, como valores exactos, cambios de estado y `pytest.raises` para errores. Por ejemplo, `gin_rummy/dealer` comprueba reparto, agotamiento del mazo y que se notifique al jugador. Sin embargo, también hay fragilidad: esa suite usa `MagicMock` para módulos completos y `fuzzywuzzy/StringMatcher` simula toda la dependencia `Levenshtein`. Los mutantes supervivientes señalan precisamente comportamientos no distinguidos por las aserciones. Por tanto, el resultado es útil como primer borrador, pero requiere revisión humana para eliminar duplicación, reducir mocks y agregar casos límite con significado.

## Comportamiento iterativo

El agente puede iterar en tres niveles: corrección de ejecución, mejora de cobertura y mejora de mutación. Los logs de la segunda ejecución permiten una aproximación más concreta, aunque no un conteo perfecto de llamadas al LLM. De 20 objetivos, 12 alcanzaron simultáneamente al menos 80% de cobertura de líneas, 50% de ramas y 50% de mutation score. En esas 12 suites se observaron 43 intentos de `pytest` hasta obtener una suite ejecutable, aproximadamente 3,6 intentos por objetivo. El mínimo fue 2 intentos y el máximo 9; por ejemplo, `blackjack/base` llegó al resultado en 2, mientras `mahjong/game` necesitó 9. Esto incluye la generación inicial y las correcciones solicitadas mediante `build_fix_prompt`.

Después de que `pytest` pasó, las suites exitosas requirieron normalmente una medición de cobertura y una de mutación: la cobertura inicial ya superaba el umbral y el primer mutation score también lo hacía. Si se cuentan estas fases de evaluación junto con los intentos de `pytest`, el promedio aproximado es 5,6 ejecuciones de validación por suite exitosa. No debe confundirse este número con llamadas exactas al LLM: el agente no conserva un contador histórico de prompts, y una medición no implica necesariamente una nueva respuesta del modelo.

Los fallos iniciales se explican por imports ausentes, APIs inferidas incorrectamente, aserciones incompatibles y dependencias externas. En los casos que no llegaron a las metas, los logs muestran hasta 8 intentos fallidos de `pytest`, errores 503 por alta demanda y agotamiento del límite de 105 segundos. La mutación también es sensible al tiempo: en una ejecución `mahjong/player` obtuvo 15% y luego 80%, mientras `blackjack/dealer` pasó de 14% a 18% y finalmente otra corrida alcanzó 82%; los `timeouts` producen resultados parciales. Además, cuando el candidato de refuerzo de mutación rompió `pytest`, el agente lo descartó. Por ello, estos promedios describen el comportamiento observado y no una garantía reproducible. Para medirlo rigurosamente se debe registrar por llamada el `attempt`, duración, resultado de `pytest`, score anterior y score posterior.

Por último, se tiene que considerar que incluso cuando las iteraciones pueden partir realizandose correctamente, la dependencia a una API de alto flujo, muchas solicitudes y en una capa gratuita puede afectar a los resultados. En muchas instancias o no lograba conectarse y entregar los resultados o en una iteración que buscaba mejorar las métricas dejó de recibir respuestas y no logró llegar al umbral o calcular el mutation score, por lo que también son parte de las limitaciones al iterar.
